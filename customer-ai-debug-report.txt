Build blocker being addressed: `git clone` of the Hermes agent failed in the
Blitz Cloud build with
  fatal: could not read Username for 'https://github.com': No such device or
  address / fatal: expected flush after ref listing (exit 128).
Diagnosis: the repo reference itself is CORRECT and PUBLIC. During the failed
build, GitHub answered the HTTPS ls-remote with an auth-required (404) response
(repo transiently private/absent at that moment — the repo is actively pushed
2026-09-23 17:01 UTC), so git tried to prompt for a username; in a headless
build with no terminal this becomes "could not read Username … No such device
or address". The Dockerfile is now hardened so the build never attempts an
interactive credential prompt: it either clones or fails fast (see section 2).
The exact Git sequence now passes reachability + checkout verification (section
7). A real `docker build` could not be executed here (no daemon), so image-level
verification remains with the operator.

================================================================================
2. ROOT CAUSE
================================================================================
1. Dockerfile pins HERMES_REPO=https://github.com/NousResearch/hermes-agent.git
   and HERMES_COMMIT=4716ec0ba4e212105f8f162c226f052b25f8a76b (public repo).
2. On the failing build, GitHub responded to the anonymous git-over-HTTPS
   ls-remote with 404 (private/nonexistent at that instant), which git
   interprets as "authentication required".
3. With no credential helper and no terminal in the build, git's getpass fails:
   "could not read Username … No such device or address" -> the RUN aborts
   (exit 128). This is a credential-PROMPT symptom, not an invalid URL/commit.
4. Verified NOW: the repo is public (private: false), and the exact sequence
   clone --no-checkout --depth 1 + fetch --depth 1 <sha> + checkout --detach
   succeeds, HEAD at 4716ec0 (hermes-agent v0.21.3). The repository was created
   2025-07-22 and pushed as recently as 2026-09-23 17:01 UTC — consistent with
   it being made public/available again right before this inspection.
Conclusion: no secret is required and no secret belongs in the build. The fix is
to never let git interactively request credentials in the (headless) build, so
an unavailable/private-again repo fails fast with a clear error instead of the
confusing fatal, and a public repo clones as it does today.
