HOW /hermes-dashboard ROUTES TO 9119
------------------------------------------------------------------------------
Browser:  https://<blitz-host>/hermes-dashboard
   -> Customer AI Express (port 8080)
   -> app.use('/hermes-dashboard', hermesDashboardProxy)   [server.js:7]
   -> strip the prefix, inject X-Forwarded-Prefix, forward to
      http://127.0.0.1:9119 via node:http
   -> Hermes dashboard (FastAPI/uvicorn) responds, response streamed back

Effective command, for reference:
  hermes dashboard --host 0.0.0.0 --port 9119 --no-open
(supervisor.mjs:88-109). The dashboard stays bound to 0.0.0.0:9119 and is
simply not published by Blitz; the proxy is the only public door to it.

KEY INSIGHT (why this works cleanly): Hermes has FIRST-CLASS reverse-proxy
sub-path support built in, keyed off one header. Injecting
`X-Forwarded-Prefix: /hermes-dashboard` makes the dashboard, with no rebuild:
  - inject window.__HERMES_BASE_PATH__="/hermes-dashboard"
    (web_server_dashboard.py:140-172) so the SPA builds prefixed URLs;
  - rewrite the absolute Vite asset URLs baked into index.html —
    href="/assets/, src="/assets/, /favicon.ico, /fonts/, /ds-assets/
    (web_server_dashboard.py:163-167);
  - rewrite url(/fonts/...) etc. inside hashed CSS
    (web_server_dashboard.py:177-190);
  - scope session cookies to the prefix: Path=/hermes-dashboard and the
    __Secure- cookie-name variant (dashboard_auth/cookies.py:47-60);
  - build prefixed Location headers and OAuth redirect URIs
    (dashboard_auth/prefix.py).
The dashboard also rejects '..', '//' and quote/space/CRLF characters in the
prefix, so a hostile value cannot smuggle HTML or traversal. Our proxy always
OVERWRITES the header, so a client cannot inject its own prefix.

1. FILES CHANGED
------------------------------------------------------------------------------
A) server/src/middleware/hermesDashboardProxy.js  (NEW, ~30 lines of code)
   Exports:
     HERMES_DASHBOARD_PREFIX  = '/hermes-dashboard'
     hermesDashboardProxy     = Express middleware for normal HTTP
     attachHermesDashboardProxy(server) = attaches the 'upgrade' handler
   Behaviour:
     - Gated on the SAME env flag the container supervisor already uses
       (HERMES_DASHBOARD = true|1|yes, case-insensitive, default OFF), so the
       process and the route can never disagree. When unset the middleware calls
       next() and the upgrade listener is never attached — a total no-op.
     - Target is 127.0.0.1:${HERMES_DASHBOARD_PORT:-9119}, reusing the
       Dockerfile:62 default. Loopback only, never a routable address.
     - Strips the prefix segment-safely (so /hermes-dashboardfoo is NOT matched)
       and preserves the query string.
     - Forwards method, body and headers. Bodies are piped as a raw stream.
     - Sets x-forwarded-prefix (always, overwriting any client value),
       x-forwarded-host, x-forwarded-proto, x-forwarded-for. Express's
       req.protocol is preferred for the scheme because app.set('trust proxy')
       is on, so a client cannot spoof it.
     - Strips hop-by-hop headers per RFC 9110 7.6.1 (connection, keep-alive,
       proxy-authenticate, proxy-authorization, te, trailer, transfer-encoding,
       upgrade) so a client cannot desync the upstream connection.
     - Rewrites root-relative Location headers to stay inside the prefix
       (safety net for redirects), and NEVER double-prefixes a Location that
       Hermes already prefixed.
     - Upstream unreachable -> 502 with a generic message. The real error
       (e.g. ECONNREFUSED) is logged server-side only and never returned.
     - WebSocket support: the dashboard SPA uses /api/ws and /api/pty, so without
       upgrade proxying the page would load but live updates and the terminal
       would be dead. The upgrade handler rewrites the 101 response manually and
       splices both the client's and the upstream's early bytes back onto the
       socket in the correct order. An upgrade outside the prefix is destroyed,
       not hijacked.

B) server/src/server.js  (3 edits, all additive)
   1. +1 import of the three symbols.
   2. +1 app.use(HERMES_DASHBOARD_PREFIX, hermesDashboardProxy) at line 7, placed
      deliberately BETWEEN helmet() and cors()/express.json():
        - AFTER helmet  -> the dashboard still gets the standard security
          headers (HSTS, X-Frame-Options, nosniff, referrer-policy, ...).
        - BEFORE express.json() -> CRITICAL. The dashboard's onboarding and
          auth calls POST JSON; if express.json() had already consumed the body,
          the proxy would forward an empty body and pairing would silently
          break. Mounting before it keeps the stream raw.
        - BEFORE the SPA catch-all app.get(/^(?!\/api).*/) on line 13, which
          would otherwise answer /hermes-dashboard with Customer AI's
          index.html.
      Ordering of every pre-existing middleware is otherwise unchanged.
   3. Replaced the two inline app.listen() calls with a small serve(message)
      helper so the http.Server object is available to attach the upgrade
      handler. Both original log messages (normal and "degraded mode") and the
      degraded-mode fallback are preserved exactly.

C) Unchanged on purpose: server/package.json, server/package-lock.json (no new
   dependency — node:http and node:net only), all routes, auth middleware,
   client code, Dockerfile, supervisor.mjs, entrypoint.sh, render.yaml.

3. SECURITY NOTES / TRADE-OFFS
------------------------------------------------------------------------------
- ONE deliberate header change: Content-Security-Policy is removed from
  dashboard responses only. helmet 8.3.0 defaults to `script-src 'self'` with
  no 'unsafe-inline', which would block the inline bootstrap <script> Hermes
  injects into index.html (session token + __HERMES_BASE_PATH__). Without the
  removal the dashboard renders blank. Every other helmet header still applies,
  and no CSP change was made for any other route. This was the only way to keep
  helmet active everywhere else.
- The proxy is same-origin only. It is reachable at /hermes-dashboard on the
  same public host as the Customer AI app, so anyone who can reach the app can
  reach the login page. Hermes' gate is the boundary — which is exactly the
  existing design. If you want a second factor, put Cloudflare Access or an
  IP allowlist in front of the whole host.
- The internal upstream is hardcoded to 127.0.0.1, so the dashboard is not
  reachable from outside the container by any other route.
- morgan does not log dashboard traffic (it is mounted after the proxy) and the
  /api rate limiter does not apply to it. If you want pairing attempts visible
  in the Customer AI logs, the dashboard's own audit log is the place to look.
- x-forwarded-proto defaults to https when the platform does not send it. That
  is the stricter choice (Secure/__Secure- cookies). If Blitz forwards it
  correctly it is used instead. If the chain is ever unreliable, set
  HERMES_DASHBOARD_PUBLIC_URL to the full public URL including the prefix —
  that is the official override and it takes precedence.

5. TO ACTUALLY USE IT ON BLITZ
------------------------------------------------------------------------------
Set these service env vars (no port change needed):
  HERMES_DASHBOARD=true
  HERMES_DASHBOARD_PORT=9119                (optional; this is the default)
  HERMES_DASHBOARD_BASIC_AUTH_USERNAME=<user>
  HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=<strong secret>
Then open https://<blitz-host>/hermes-dashboard and log in. The dashboard's
Basic Auth gate cannot be disabled on a 0.0.0.0 bind, and we do not attempt to
bypass it. Reminder from the previous report: also set WHATSAPP_SETUP_TOKEN —
server/src/routes/whatsapp.js:4 is fail-open when it is unset (latent; nothing
sits behind it today, and this change adds nothing).

Pairing remains a ONE-TIME action. After it, creds.json lives at
/app/data/hermes/platforms/whatsapp/session/creds.json on the persistent disk
and the gateway reconnects on every restart with no dashboard needed. You can
turn HERMES_DASHBOARD off afterwards to remove the public door entirely.

Note (carried over, unchanged): applying a pairing makes Hermes restart the
gateway (web_server_messaging.py:371-373), which the supervisor reads as an
unexpected gateway exit -> one container restart, then it comes up paired.
Self-healing; a clean fix would be out of scope for this change.
