4. DOCKER BUILD FIX 2 — root-owned /home/customerai/.npm cache (EACCES)
================================================================================
Root cause chain (static analysis of the Dockerfile instruction sequence):
  - ENV HOME=/home/customerai (line 48) applies to EVERY later step, including
    those that still run as root.
  - The backend `RUN npm ci --omit=dev` runs as ROOT (USER customerai only
    comes later), so npm creates its cache at $HOME/.npm =
    /home/customerai/.npm OWNED BY UID 0.
  - The earlier `chown -R customerai:customerai ... /home/customerai` happens
    BEFORE that npm step, so it cannot protect the cache directory.
  - The WhatsApp-bridge `RUN npm ci --prefix
    /opt/hermes-agent/scripts/whatsapp-bridge` is the FIRST npm command that
    runs as customerai (uid/gid 1000); npm tries to open a root-owned cache
    tmp file -> EACCES (-13), aborting the build (the reported "step #27").
Fix applied (one line, Dockerfile line 99):
    RUN chown -R customerai:customerai /home/customerai
  placed between the root `npm ci --omit=dev` and `USER customerai`, so the
  home dir (including any root-created cache) is uid/gid-1000 before any
  customerai npm/uv/launcher step touches it.
Why safe for the uid/gid-1000 design:
  - Re-establishes the ownership the Dockerfile already declares (lines 85-94);
    it only removes uid-0 leftovers that npm created at build time.
  - Runs at BUILD time, as root build context only; the FINAL runtime remains
    `--user 1000:1000 --cap-drop ALL --security-opt no-new-privileges` — no
    sudo, no root container, no world-writable home, no persistence change.
  - The persistent volume /home/customerai/.hermes and its sealing on first
    boot are untouched; uid 1000 still owns /home/customerai at runtime.
  - Hermes venv/uv, bridge npm deps, backend node_modules (root-owned, read-only
    at runtime), entrypoint, supervisor, and healthcheck are unchanged.
Other root-owned npm cache locations checked:
  - Stage 1 (client-build): `npm ci` and `npm run build` run as root with
    HOME=/root (no ENV HOME override in that stage) -> cache at /root/.npm.
    That stage terminates after COPY --from; nothing runs as uid 1000 there.
    NOT a problem.
  - Stage 2: the ONLY root npm step is `npm ci --omit=dev`; its cache,
    /home/customerai/.npm, is the one fixed. The bridge npm step runs as uid
    1000 and now uses a uid-1000 cache.
  - node-gyp/native-build cache (~/.node-gyp): no native deps — server and
    client package.json are pure-JS (bcryptjs, mongoose, groq-sdk, vite, react,
    no node-gyp/better-sqlite3/sharp/bcrypt/etc.), and the chown -R also covers
    ~/.node-gyp should it ever appear.
  - No other cache dirs: uv runs as customerai (-> ~/.cache/uv), and the
    launcher printf runs as customerai. Nothing else writes to home as root.
PASS (static) — Dockerfile still parses under hadolint: no syntax errors; only
  DL3008 (apt pin) + DL4006 (pipefail) warnings (pre-existing) and one
  informational DL3059 suggesting RUN consolidation (kept separate on purpose so
  the root-npm layer and the ownership-fix layer remain independently cached).
UNVERIFIED — actual `docker build` (daemon inaccessible; see section 16).
