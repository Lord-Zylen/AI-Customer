LATEST UPDATE (2026-09-28, 2nd pass): The prebuild step I added did not build on
Blitz. `npm ci` succeeded but `tsc -b` failed with 91 errors. Reproduced the
failure exactly and found the cause: the build was missing devDependencies,
because our own Dockerfile sets NODE_ENV=production. Fixed by adding ONE npm flag.
This is a second, independent bug — the first one (dashboard blocking before it
binds) was real and is still what caused the 502; the second is what stopped the
prebuilt dist from being produced in the first place.

  ISSUE 2 (this pass) — web build fails, missing modules
  ROOT CAUSE: `ENV NODE_ENV=production` at Dockerfile:52. npm treats
  NODE_ENV=production as omit=dev, so the install silently pruned every
  devDependency. The web build toolchain is declared as devDependencies
  (web/package.json): typescript 6.0.3, vite 8.2.0, @vitejs/plugin-react 6.0.3,
  vitest 4.1.10, @rolldown/plugin-babel 0.2.3, @types/node 22.20.1, and
  @types/qrcode. `npm ci` therefore exits 0 having installed a partial tree
  (exactly 356 packages), and only the subsequent `tsc -b` reveals the damage.

  WHY 356 PACKAGES: that is the non-dev subset of the tree reachable from the
  three selected workspaces. The full closure is 551 packages. Nothing is
  "missing from the lockfile" — every missing module is present in
  package-lock.json and correctly marked dev:true, e.g.
      web/node_modules/@rolldown/plugin-babel  [dev]
      node_modules/vitest                      [dev]
      node_modules/@vitejs/plugin-react        [dev]
      node_modules/@types/qrcode               [dev]
  dev:true entries are omitted under NODE_ENV=production. The packages still
  present (vite, typescript, qrcode) are only there because they are hoisted
  prod copies required by OTHER workspaces in the closure — which is why tsc
  itself could RUN and then failed to resolve things.

  Hermes hits this exact trap and guards against it the same way we now do.
  main_web_build.py:313-341, _run_npm_install_deterministic(), docstring:
      "--include=dev is forced: an inherited NODE_ENV=production / omit=dev
       silently skips the build toolchain and the build dies with tsc: not found"
  and line 335 appends --include=dev to EVERY npm invocation it makes. My
  original Dockerfile line reproduced the command but dropped that flag.

  FIX (one flag, Dockerfile only):
      RUN npm ci --workspace ui-tui --workspace web --include-workspace-root --include=dev \
       && npm run build -w web

  NO package.json / package-lock.json CHANGE IS NEEDED OR MADE. The lockfile is
  correct and self-consistent; the install was simply being told to skip half of
  it. Nothing added to the Customer AI project either — this is entirely inside
  the pinned Hermes image. No audit fix, no tsconfig relaxation, no test removal,
  no skipLibCheck, no vendored dist.

ISSUE 1 (earlier pass) — the 502: dashboard never bound 9119
------------------------------------------------------------------------------
The proxy was never the problem — it correctly reported ECONNREFUSED because
nothing was listening. `hermes dashboard` blocks BEFORE it binds, on a mandatory
frontend build that can never complete in this image.

  EXACT REASON
  main_dashboard.py:808 _resolve_dashboard_web_dist() runs before the server is
  imported, and at line 821-823:

      elif "HERMES_WEB_DIST" not in os.environ and not skip_build:
          if not _build_web_ui(PROJECT_ROOT / "web", fatal=True):
              sys.exit(1)

  Our invocation sets neither HERMES_WEB_DIST nor --skip-build, so it takes this
  branch and performs a MANDATORY, BLOCKING build of the `web` workspace
  (`npm install` + `tsc -b && vite build`). The image shipped neither
  hermes_cli/web_dist nor the web workspace's node_modules, so that build could
  not finish. Uvicorn is never started, port 9119 is never bound, and the
  Customer AI proxy's upstream connect gets ECONNREFUSED -> 502.
  (With issue 2 now understood, the precise statement is: the runtime build could
  not complete because devDependencies were absent by the same NODE_ENV rule, and
  the .web_ui_build.lock made that failure silent rather than loud.)

FIX (Dockerfile only, 2 added statements):

   && npm run build -w web
  ENV HERMES_WEB_DIST=/opt/hermes-agent/hermes_cli/web_dist
With HERMES_WEB_DIST set, main_dashboard.py:853 takes the "caller-managed dist"
branch and SKIPS the build entirely; web_server.py:58 then serves the SPA from
that path. No proxy, pairing, auth or supervisor change was needed.

2. THE TWO-LAYER FAILURE (why it is silent, and why it is fatal)
------------------------------------------------------------------------------
Layer 1 — the lock (main_web_build.py:405-419). Any Hermes process that wants to
build the web UI takes an flock on <project_root>/.web_ui_build.lock:
    flock(LOCK_EX | LOCK_NB)
      success            -> this process builds
      failure + dist OK  -> serve the existing dist (return True)
      failure + no dist  -> flock(LOCK_EX)  <-- BLOCKS FOREVER, silently
The supervisor starts the gateway (supervisor.mjs:159) BEFORE the dashboard
(:162). The gateway is a Hermes process that can hold that lock, so the dashboard
hits the third case and waits indefinitely with zero output. Note this is a
symptom amplifier, not the root cause: with a prebuilt dist the branch is never
reached at all.

Layer 2 — the build itself cannot succeed in this image. Even holding the lock,
`_do_build_web_ui` must install the `web` workspace and then run `npm run build`
(`tsc -b && vite build`). The image has no web workspace node_modules, so that
install must reach the registry at runtime — unavailable/slow in the container,
and unbounded, so it hangs rather than failing. And per issue 2 above, even when
it does run under NODE_ENV=production it installs an incomplete tree and then
fails loudly at tsc instead. Note npm's output is only relayed on FAILURE
(_relay_npm_output is called from _report_web_build_failure), so a hanging install
is silent by construction.

5. THE FIX
------------------------------------------------------------------------------
Dockerfile, inserted after the WhatsApp bridge npm ci (:139), before the
`hermes` launcher RUN. Runs as `customerai` (USER at :127) into /opt/hermes-agent
(chowned to customerai at :108), so no new root-owned tree is introduced.

    RUN npm ci --workspace ui-tui --workspace web --include-workspace-root --include=dev \
     && npm run build -w web
    ENV HERMES_WEB_DIST=/opt/hermes-agent/hermes_cli/web_dist

Why this closure: it mirrors hermes_cli/main_web_build.py::_web_npm_install_context
exactly, which is documented as required — the root package.json workspaces are
["apps/*","ui-tui","ui-tui/packages/*","web","tests-js"], and that helper returns
("--workspace","ui-tui","--workspace","web","--include-workspace-root"). A
narrower install would silently prune deps the build needs (see the #43564/#64354
note in the source). The build's vite outDir is already ../hermes_cli/web_dist,
so the output lands exactly where HERMES_WEB_DIST points.

Why --include=dev: see issue 2. It is what Hermes itself forces
(main_web_build.py:335). The one-token change is the entire fix for the Blitz
build failure; the ENV line is unchanged from the previous pass.

Deliberately NOT changed: the proxy (server/src/middleware/hermesDashboardProxy.js),
server.js, supervisor.mjs, the pairing architecture, auth, the /api/whatsapp/*
routes, the frontend, MongoDB, and the dashboard command line itself.

7. TRADE-OFFS / THINGS TO EXPECT
------------------------------------------------------------------------------
- IMAGE SIZE AND BUILD TIME INCREASE. This is the unavoidable cost of a working
  dashboard UI: the `web` workspace node_modules (551 packages) plus the built
  dist. Measured locally, npm ci ~60s and vite build ~53s, so expect the Docker
  build to grow by a couple of minutes. I did not prune dev dependencies
  afterwards: it would shrink the image but risks removing something the
  dashboard needs, and minimality was the priority. Easy to revisit.
  The dev deps are build-time only and are not needed at runtime now that the
  dist is baked in, so a later `npm prune --omit=dev` after the build is the
  natural follow-up if image size becomes a problem.
- The dashboard needs ~24-30s to become ready after the container starts. The
  proxy will return 502 during that window; this is expected, not a regression.
- HERMES_DASHBOARD still must be enabled for the supervisor to start the process,
  and HERMES_DASHBOARD_BASIC_AUTH_USERNAME / _PASSWORD remain mandatory. With the
  fix in place the dashboard now fails FAST and loudly if the dist is missing
  (sys.exit(1)) instead of hanging — a strictly better failure mode.
- A fresh `npm ci` runs at image build. If the web sources change, rebuild the
  image; there is no runtime rebuild path any more, which is the point.
- The gateway's .web_ui_build.lock is now irrelevant to the dashboard, since the
  build path is never entered. No lock cleanup or stale-lock handling is needed.
