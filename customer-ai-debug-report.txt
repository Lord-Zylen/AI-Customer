===============================================================================
1. WHY THIS WAS THE RIGHT (MINIMAL) FIX
===============================================================================
Pairing lives entirely in the pinned Hermes agent, NOT in this repo. The repo's
/hermes/ directory contains only templates (config.yaml, plugin, hook) and no
pairing code. The locally installed agent at ~/.hermes/hermes-agent is at commit
4716ec0, which EXACTLY matches the Dockerfile pin, so all agent-level findings
below are authoritative for the production image.

Two pairing entry points exist, both in the agent:
  (a) CLI   `hermes whatsapp`  ("Set up WhatsApp integration"; also cited by
          plugins/platforms/whatsapp/adapter.py:446 and :459)
  (b) Web   Hermes dashboard JSON API, hermes_cli/web_routers/messaging.py:
          :546 POST /api/messaging/whatsapp/onboarding/start
          :580 GET  /api/messaging/whatsapp/onboarding/{pairing_id}
          :589 POST /api/messaging/whatsapp/onboarding/{pairing_id}/apply
          :621 cancel endpoint
      The QR is produced by the Baileys bridge itself, spawned at
      messaging.py:391-414 as:
          node <bridge>/bridge.js --pair-only --pair-json --session <session_path>
      with WHATSAPP_MODE and WHATSAPP_DM_POLICY=pairing. --pair-json emits
      newline-delimited JSON; _apply_pairing_event() (messaging.py:438-460) maps
      the "qr" event into record.qr_payload, returned by
      web_server_messaging.py:367-368. This is the machine-readable path a
      headless platform needs, and it already exists.

Why the platform could not pair before:
  - supervisor.mjs started only the backend and the gateway; no dashboard.
  - HERMES_DASHBOARD is s6-overlay-only. hermes_cli/subcommands/gateway.py
    (--no-supervise help) states gateway supervision "plus a supervised
    dashboard if HERMES_DASHBOARD is set" is an s6-overlay feature with "No
    effect outside an s6 container". This image is node:22-bookworm-slim driven
    by supervisor.mjs and has no s6, so the variable was inert.
  - The QR could not be recovered from logs either. adapter.py:449-465
    _preflight() treats a missing creds.json as a NON-RETRYABLE fatal error (it
    never prints a QR; it just says "pair from the dashboard or run `hermes
    whatsapp`"), and supervisor.mjs makeLogger() prefixes every line, which
    destroys a terminal-rendered QR matrix.

Customer AI's own /api/whatsapp/* routes were deliberately left untouched:
getWhatsAppQr() returns null (server/src/services/whatsapp.service.js:81-83) so
/qr 404s, and connect/disconnect/reset throw 409 (:85-95). This matches
README:67,133 and the single-transport rule in WhatsAppSetup.jsx:9
("Customer AI never pairs a second device"). Pairing stays in Hermes.

4. SECURITY
===============================================================================
The dashboard binds 0.0.0.0, so Hermes engages its auth gate and will REFUSE to
start on a non-loopback bind unless an auth provider is registered. Only two
zero-infrastructure options exist:
    HERMES_DASHBOARD_BASIC_AUTH_USERNAME + HERMES_DASHBOARD_BASIC_AUTH_PASSWORD
    HERMES_DASHBOARD_OAUTH_CLIENT_ID
`--insecure` was removed from the June 2026 hardening and is now a NO-OP; the
supervisor passes no such flag and no code path attempts to bypass
authentication. A recursive grep confirms the only occurrence of the string
"insecure" in either changed file is the comment stating we never use it.
This is defence in depth, not a workaround: the dashboard is a separate process
on a separate port from the Customer AI Express server, and Customer AI's own
JWT auth is completely unaffected.

Separately, and still worth fixing at some point: server/src/routes/whatsapp.js:4
requireSetupToken is FAIL-OPEN — `if (!process.env.WHATSAPP_SETUP_TOKEN || ...)`
passes for any caller when the token is unset. Harmless today because every
route behind it is a 409/404 stub, and this change does not add anything behind
it. But set WHATSAPP_SETUP_TOKEN regardless, and make that guard fail-closed
before anyone ever places real capability behind it.

===============================================================================
5. REQUIRED OPERATOR STEPS (NOT DONE — NO DEPLOY CONFIG WAS TOUCHED)
===============================================================================
These are platform-level and live outside this repo, so they were intentionally
not edited. They are REQUIRED for pairing to work on Blitz:

  1. Set env on the Blitz service:
         HERMES_DASHBOARD=true
         HERMES_DASHBOARD_BASIC_AUTH_USERNAME=<something>
         HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=<strong secret>
     (HERMES_DASHBOARD_PORT only if you want something other than 9119.)
  2. PUBLISH PORT 9119. EXPOSE 9119 alone does not open anything. Most hosts
     route only ONE port publicly, so either publish 9119 as a second port with
     the basic-auth credentials, or front it with a reverse proxy. Do NOT expose
     it unauthenticated — Hermes will refuse to start.
  3. Set WHATSAPP_SETUP_TOKEN as defence in depth (see section 4).
  4. Redeploy, then open the dashboard -> Messaging -> WhatsApp -> Start setup,
     poll the onboarding endpoint, scan the QR, then apply.

Pairing is a ONE-TIME operation. Afterwards creds.json lives on the persistent
disk and the gateway reconnects on every restart with no dashboard needed.

7. OPEN ITEMS / RISKS
===============================================================================
- RESOLVED: first-time WhatsApp pairing on a console-less platform. The QR is
  now reachable over authenticated HTTP via the Hermes dashboard.
- R1 (MEDIUM, operational): web_server_messaging.py:371-373
  _restart_gateway_after_whatsapp_onboarding() restarts the gateway when you
  apply a pairing. The supervisor owns the gateway, so that restart surfaces as
  an unexpected gateway exit -> shutdown(1) -> one container restart, after
  which the gateway starts already-paired. Self-healing, but expect one restart
  right after you hit apply. A clean fix is to let the supervisor ignore gateway
  exits it did not initiate; that was out of scope for this change and is
  deliberately not implemented.
- R2 (MEDIUM, latent security): routes/whatsapp.js:4 requireSetupToken is
  fail-open when WHATSAPP_SETUP_TOKEN is unset. Not exploited today; set the
  token and make the guard fail-closed.
- R3 (MEDIUM, documentation): WHATSAPP_AUTH_DIR is set in Dockerfile:63,
  exported by entrypoint.sh:19, mkdir'd and documented in README:52 and
  .env.example, but the pinned agent has ZERO references to it. Hermes ignores
  it. The real credential store is
  /app/data/hermes/platforms/whatsapp/session/creds.json. Persistence is not at
  risk (both are under /app/data) but the docs point operators at the wrong
  directory. Worth correcting in a later pass.
- R4 (LOW): dashboard onboarding records live in Hermes' in-memory map and
  expire (_WHATSAPP_ONBOARDING_TTL_SECONDS). A QR left too long before scanning
  must be regenerated via a new start call.
- R5 (LOW): dashboard and gateway share $HERMES_HOME; losing the /app/data disk
  still forces re-pairing. Existing persistence guarantees unchanged.
- R6: the /api/health 503 (MongoDB) and the ADMIN password work are separate
  open items, untouched by this change. Note the supervisor only starts Hermes
  after /api/health returns 200, so pairing is also gated on a healthy DB.
