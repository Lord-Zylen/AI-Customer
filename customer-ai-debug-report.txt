4. DOCKER BUILD FIX 2 — root-owned /home/customerai/.npm cache (EACCES)
================================================================================
Exact failing command (build step #27): the WhatsApp-bridge
  RUN npm ci --prefix /opt/hermes-agent/scripts/whatsapp-bridge   (line 123)
Why it IS the failing command: the error is EACCES opening
  /home/customerai/.npm/_cacache/tmp/... — an EACCES on a cache write can only
  come from a process running as a non-root user. The ONLY npm command that
  runs as `customerai` (uid/gid 1000) is the bridge npm ci. The backend
  `npm ci --omit=dev` (line 98) runs as ROOT (the base image node:bookworm-slim
  does NOT set USER; our `USER customerai` only applies at line 111) — root
  cannot produce EACCES. (Builder step numbers vary by frontend/internal steps;
  the identity of the failing statement is unambiguous from the error.)

Complete inventory of every npm command in the Dockerfile:
  1. line 35  `npm ci`             stage 1, root,   HOME=/root   (scratch stage)
  2. line 37  `npm run build`      stage 1, root,   HOME=/root   (scratch stage)
  3. line 98  `npm ci --omit=dev`  stage 2, root,   HOME=/home/customerai
                                             ^^^^^  THE cache creator (root-owned)
  4. line 123 `npm ci --prefix …`  stage 2, customerai, HOME=/home/customerai
                                             ^^^^^ the EACCES victim (#27)
Stage 1 npm uses /root (no ENV HOME in that stage, scratch container, terminates
after COPY --from) -> NOT a problem. No .npmrc exists in the repo or image.

Root-to-non-root ownership sequence that caused the failure (before this fix):
  a) ENV HOME=/home/customerai (line 48) applies to EVERY later step, root or
     not, so npm's default cache (os.homedir()/$HOME -> ~/.npm) is
     /home/customerai/.npm for every npm process in stage 2.
  b) usermod/groupmod (lines 79-83) move /home/node (uid 1000) to
     /home/customerai, then line 93-94 chown -R's it to customerai. Homes start
     correctly owned.
  c) line 98 runs as ROOT (USER only at 111); its `npm ci` creates
     /home/customerai/.npm and writes _cacache CONTENT AS UID 0.
  d) line 123 runs as customerai (uid 1000); npm tries to open a file inside
     the root-owned _cacache/tmp -> EACCES -13 -> build aborts.
  The earlier plain `chown -R /home/customerai` was ordered before #27 but the
  requirement is to explicitly REMOVE the root-owned cache and re-create it with
  1000:1000 ownership before the non-root npm; a bare chown is not sufficient
  acceptance for this failure class.

The fix (Dockerfile lines 98-101), placed BEFORE `USER customerai` (line 111)
and therefore BEFORE step #27 (line 123):
  RUN npm ci --omit=dev
  RUN rm -rf /home/customerai/.npm \
      && mkdir -p /home/customerai/.npm \
      && chown -R customerai:customerai /home/customerai
  - line 98 (root) may still populate the cache; that cache is then thrown away.
  - lines 99-101 delete the root-owned cache, create /home/customerai/.npm, and
    own the entire home (incl. the cache) as uid/gid 1000.
  - at #27 the cache already exists with UID/GID 1000 and no root-owned content;
    npm-as-customerai creates fresh content owned by 1000 -> no EACCES.
  - redundancy: even if another root step ever re-rooted the home, line 99-101
    runs immediately before the non-root npm and re-establishes 1000:1000.
Also verified (local, as uid 1000): npm, run by a 1000-uid user against a cache
directory it owns, writes the cache successfully (no EACCES) — the exact
end-state #27 now sees.

Other root-owned npm cache locations checked (requirement 15):
  - Stage 1 `npm ci`/`npm run build`: root, HOME=/root, scratch stage, never
    re-entered by a non-root step -> not a problem.
  - Stage 2 root `npm ci --omit=dev`: a) causes the home cache to be root-owned;
    covered by the reset at lines 99-101. No subsequent root npm exists after
    that reset (USER customerai at 111; the only later npm is the bridge, as 1000).
  - node-gyp/native builds: none (server/client deps are pure JS; no node-gyp,
    sharp, bcrypt, better-sqlite3, etc.); the chown -R also covers ~/.node-gyp
    if ever introduced.
  - uv operates as customerai (-> ~/.cache/uv); launcher printf as customerai.
    No other root-owned cache paths.

Why the fix is safe for the UID/GID 1000 runtime design:
  - Ownership is set at BUILD time while root only for the purpose of writing
    the image layer; the FINAL container still runs `--user 1000:1000
    --cap-drop ALL --security-opt no-new-privileges`. No sudo, no root runtime,
    no world-writable home.
  - The persistent volume /home/customerai/.hermes and its first-boot seeding
    are untouched; the runtime user is still exactly uid/gid 1000.
  - /app/server/node_modules stays the build-time root-owned, read-only tree the
    design documents (only /home is re-owned). Hermes venv, bridge npm deps,
    backend, frontend, entrypoint, supervisor, healthcheck, and security
    configuration are unchanged.
  - Cache is throwaway build state; deleting it costs only a re-download during
    the customerai npm step (expected behavior of the reset approach).
